## Часть I. Контекст проекта

### Что за система

`tea-production-db` — веб-приложение и БД производства чая.

- **БД:** Supabase (PostgreSQL)
- **Frontend:** React + Vite + Tailwind, автодеплой на Vercel из `main`
- **Backend:** Supabase Edge Functions (Deno) + Anthropic API
- **Структура:** `app/` (фронт), `api/` (серверные роуты), `supabase/functions/`,
  `supabase/migrations/`, `migration/django/` (read-only витрина на Django)
- Документация и архив выгрузок — в приватном репозитории `andmanuylov-ftc/tea-production-data`

### Схема БД (миграция 001)

```
material_categories     — категории сырья
raw_materials           — сырьё и материалы (article UNIQUE, name, category_id, unit «кг»/«шт», supplier)
material_prices         — цены на сырьё с историей (material_id, price_per_unit, valid_from, valid_to)
recipes                 — рецепты, выход 1 кг (article UNIQUE, output_quantity, output_unit)
recipe_ingredients      — состав рецепта (recipe_id, material_id, quantity, unit)
products                — готовая продукция / SKU (article UNIQUE, recipe_id, package_size, package_unit)
sku_recipe_components   — состав SKU (product_id, recipe_id, material_id, quantity)
price_lists             — прайслисты (name, markup_percent)
price_list_items        — позиции прайслиста (price_list_id, product_id, price, override_markup_percent)
```

Разделы приложения: SKU, рецепты, материалы, ассортименты, прайс-листы (админский,
менеджерский, клиентский с бланком заказа), конструктор, описания, партнёрская программа.

### Что даёт интеграция с СБИС

В БД сейчас есть **нормативная себестоимость** (через рецепты и цены сырья) и **прайсы**.
Чего нет — **факта**: реальных продаж и реальных закупочных цен. Ценность интеграции
ровно в этом стыке: *наша себестоимость × их факт*.

Рецептур, состава SKU и нормативной себестоимости в СБИС нет и не будет — это остаётся
нашей зоной ответственности.

## Часть II. Ограничения среды разработки

**Важно для того, кто продолжит работу.**

Домены `saby.ru`, `sbis.ru`, `api.sbis.ru`, `online.sbis.ru` **заблокированы
egress-политикой** среды Claude Code (proxy отдаёт `403` на `CONNECT`,
`kind: connect_rejected`). Следствия:

1. Официальную справку нельзя прочитать напрямую — только через выдачу поиска.
2. Живой PoC против API из этой среды запустить невозможно.

Чтобы работать дальше, нужно либо разблокировать эти хосты в политике окружения,
либо гонять PoC локально / с прод-сервера.

Информация в этом документе собрана из трёх типов источников:
- **[офиц.]** — официальная справка Saby (через поисковую выдачу)
- **[втор.]** — разбор исходников публичных клиентских библиотек (npm `sbis-mcp`,
  PyPI `sbis-api-client`); в коде зашиты реальные эндпоинты и параметры, но это
  третьи лица — проверять на PoC
- **[польз.]** — материалы, которые принёс заказчик из личного изучения документации

## Часть III. Архитектура API Saby

### 3.1. Контуры

У Saby **не один API**. Ключевое разделение — по стилю и авторизации:

| | Контур JSON-RPC | Контур REST |
|---|---|---|
| Стиль | JSON-RPC 2.0, методы кириллицей `СБИС.*` и латиницей `sabyWarehouse.*` | REST, GET с query-параметрами |
| Точка входа | `POST https://online.sbis.ru/service/` (встречается `?srv=1`) | `https://api.sbis.ru/retail/...` |
| Авторизация | сессия (`sid`) или сервисный токен | сервисный токен |
| Заголовок | `X-SBISSessionID: <sid>` | `X-SBISAccessToken: <token>` |
| Content-Type | `application/json-rpc; charset=utf-8` | обычный REST |
| Что даёт | документы ЭДО, контрагенты, склады, учёт | номенклатура, прайсы, остатки, точки продаж, заказы |

Периферия: **ОФД/аренда** (`api.sbis.ru/rent/v1/...`) и **«Всё о компаниях»**
(`api.sbis.ru/vok/`, [открытая обвязка](https://github.com/saby/vok)).

**Тестовый контур:** `https://fix-online.sbis.ru` вместо `online.sbis.ru`.

### 3.2. Полный список сервисов API [польз.]

| Сервис | Что делает |
|---|---|
| API ЭДО | Электронный документооборот — отправка/получение документов, контроль статусов |

## Часть IV. Авторизация

### 4.1. Сервисная (для серверных интеграций) [офиц. + польз.]

Saby использует OAuth 2. Для фоновых программ без участия пользователя:

```jsonc
POST https://online.sbis.ru/oauth/service/
{ "app_client_id": "<ID приложения>",
  "app_secret":    "<защищённый ключ>",
  "secret_key":    "<сервисный ключ>" }

→ { "token": "<access_token>", "sid": "..." }
```

Дальше в каждом запросе: `X-SBISAccessToken: <access_token>`.

Отзыв токена: `POST https://online.sbis.ru/oauth/service/` с телом
`{"event": "exit", "token": "<access_token>"}`. [втор.]

### 4.2. Интерактивная (через браузер, с участием пользователя) [польз.]

```
https://online.sbis.ru/oauth/api/token
  ?client_id=<client_id>
  &redirect_uri=<redirect_uri>
  &response_type=code|token
  &state=<state>
  &scope=openid profile email
```

Серверный вариант:
`https://online.sbis.ru/oauth/api/token?client_id=<client_id>&client_secret=<secret_key>`

Параметры приложения: `client_id`, `client_secret`, `redirect_uri`.

Нам для фоновой синхронизации нужна **сервисная**, интерактивная — если когда-нибудь
будем пускать пользователей в СБИС из нашего интерфейса.

### 4.3. Сессионная для ЭДО [втор.]

Альтернативный путь в JSON-RPC контур — по логину/паролю:

```jsonc
POST https://online.sbis.ru/auth/service/
Content-Type: application/json-rpc; charset=utf-8

{ "jsonrpc": "2.0", "method": "СБИС.Аутентифицировать",
  "params": { "Параметр": { "Логин": "...", "Пароль": "...", "НомерАккаунта": "..." } },
  "id": 0 }
```

В ответе `result` — строка `sid`. Дальше:

```jsonc
POST https://online.sbis.ru/service/?srv=1
X-SBISSessionID: <sid>

{ "jsonrpc": "2.0", "method": "СБИС.СписокДокументов", "params": {...}, "id": 1 }
```

Ответ — стандартный JSON-RPC: `result` при успехе, `error.message` / `error.code` при ошибке.
На `HTTP 401` — переаутентификация и повтор; на `5xx` — один ретрай.

**Время жизни сессии:** источники расходятся. Официальная справка («Порядок работы»)
— аннулирование через 24 часа простоя, максимум 7 дней. Сторонняя библиотека — ~21 день.
Практически неважно: кешируем `sid`, ловим 401, переавторизуемся.

**Что использовать нам:** на PoC проверить, покрывает ли сервисный токен
(`X-SBISAccessToken`) методы JSON-RPC контура. Если да — живём на одной авторизации;
если нет — держим обе.

## Часть V. Методы

### 5.1. ЭДО — документы

#### `СБИС.СписокДокументов` — реестр по типу и периоду

```jsonc
{ "Фильтр": {
    "Тип": "Реализация",              // обязательный
    "ДатаС": "01.06.2026",            // ДД.ММ.ГГГГ, не ISO
    "ДатаПо": "30.06.2026",
    "Направление": "Исходящий",       // Входящий | Исходящий
    "Состояние": "...",
    "Маска": "...",                   // поиск по Документ.Номер и Документ.Примечание
    "Контрагент": { "СвЮЛ": { "ИНН": "7700000000", "КПП": "770001001" } },
    "Навигация": { "Страница": "0", "РазмерСтраницы": "200" }   // ≤ 200
} }
```

Ответ:

```jsonc
{ "Документ": [ {
      "Идентификатор": "…", "Дата": "15.06.2026", "Номер": "АКТ-001",
      "Сумма": "150000.00", "Название": "…", "Тип": "Реализация",
      "Направление": "Входящий", "ДатаВремяСоздания": "15.06.2026 10.30.00",
      "Удален": "Нет",
      "Состояние": { "Код": "7", "Название": "Доставлен", "Примечание": "" },
      "Контрагент": { "СвЮЛ": { "ИНН": "…", "КПП": "…", "Название": "…" } },
      "Вложение": [ { "Идентификатор": "…", "Название": "Акт.pdf", "Тип": "АктВыпРаб" } ]
  } ],
  "Навигация": { "РазмерСтраницы": "50", "Страница": "0", "ЕстьЕще": "Нет" } }
```

Пагинация — по `Навигация.ЕстьЕще` («Да»/«Нет»), листаем `Страница`.

**Коды типов документов** [офиц.]: `ДокОтгрИсх` — документ отгрузки исходящий,
`ФактураИсх` — счёт-фактура исходящая, `АктВР` — акт выполненных работ,
`Реализация`, `Корреспонденция`. Исходящие счета-фактуры, накладные и акты
отправляются как **документы отгрузки**.

#### `СБИС.СписокДокументовПоСобытиям`

Реестры «Входящие» / «Исходящие» / «Ответы от контрагентов». Фильтр тот же, но вместо
`Тип` — `ТипРеестра`. Ответ обёрнут в `Реестр: [{ Состояние, Документ }]`.

#### `СБИС.СписокИзменений` — основа инкремента

Возвращает документы, по которым были события документооборота за период. Работает
**как курсор**: первый запрос — по `ДатаВремяС`, дальше передаём `ИдентификаторСобытия`
последнего события предыдущей страницы. Именно этот идентификатор храним в журнале
синхронизаций — не «дату последней загрузки».

#### `СБИС.ПрочитатьДокумент`

```jsonc
{ "Документ": { "Идентификатор": "…", "Редакция": { "Идентификатор": "…" } },
  "ДопПоля": "…" }
```

Возвращает последнюю (или указанную) редакцию + метаданные вложений с временными
ссылками:

```jsonc
"Вложение": [ { "Идентификатор": "…", "Название": "УПД.xml", "Тип": "УПД",
                "Файл": { "Имя": "UPD_example.xml", "Ссылка": "https://online.sbis.ru/docs/…" } } ]
```

Ссылка самодостаточна — качается обычным GET без `sid`, живёт ~1 месяц. [втор.]

#### Прочее

- `СБИС.СписокКонтрагентов` — `{"Фильтр": {"ИНН", "КПП", "Название", "Навигация"}}` →
  `Контрагент[]` с `Идентификатор`, `СвЮЛ`/`СвФЛ`, `ИдентификаторУчастника` (вида `2BM-ИНН-КПП-…`)
- `СБИС.СписокНашихОрганизаций` — свои юрлица [втор.]
- `СБИС.ИнформацияОТекущемПользователе`, `СБИС.ИнформацияОКонтрагенте`
- Запись (на первом этапе не нужна): `СБИС.ЗаписатьДокумент`, `СБИС.ЗаписатьВложение`,
  `СБИС.ПодготовитьДействие`, `СБИС.ВыполнитьДействие`
- Визуализация: представление документа в HTML/PDF по GET-ссылке из объекта «Документ»

### 5.2. Складской учёт [офиц. + польз.]

| Метод | Назначение |
|---|---|
| `sabyWarehouse.Create` | Создать карточку склада |
| `sabyWarehouse.Update` | Обновить данные склада |
| `sabyWarehouse.Read` | Получить информацию о складе |
| `sabyWarehouse.List` | Получить список складов |

Адрес запроса — `https://online.sbis.ru/service/`, **тот же JSON-RPC контур, что и ЭДО**.
`sabyWarehouse.Read` ищет карточку по идентификатору, названию или коду (нужен хотя бы

### 5.3. Retail (REST) [втор.]

| Эндпоинт | Параметры | Отдаёт |
|---|---|---|
| `GET /retail/point/list` | `pointId`, `product`, `withPhones`, `withPrices`, `withSchedule`, `page`, `pageSize` | точки продаж |

| `GET /retail/nomenclature/list` | `pointId`, `priceListId`, `withBalance`, `withBarcode`, `onlyPublished`, `page`, `pageSize` | товары и услуги по прайсу |
| `GET /retail/nomenclature/balances` | `nomenclatures[]`, `priceListIds[]`, `warehouses[]`, `companies[]` | остатки на складах |
| `GET /retail/company/list`, `/retail/company/warehouses?companyId=` | — | организации и склады |
| `GET /retail/customer/find?phone=`, `/retail/customer/{id}/bonus-balance` | — | клиенты, бонусы |

Оговорки:
- Прайс-лист отдаётся корректно только если настроен с типом **«Выбранные наименования»**
- `withBarcode: true` — способ вытащить штрихкоды, нужны для маппинга
- Встречается упоминание `/retail/v2/nomenclature/list` — уточнить актуальную версию
- Контур завязан на Saby Retail / точки продаж

### 5.4. Триггеры — это не вебхуки [офиц.]

«Триггеры» в Saby — внутренняя автоматизация бизнес-процессов: выбирается раздел и
событие (например, «Бизнес / Продажи и CRM / Сделки», событие «Полная оплата»), при
выполнении условия Saby сам совершает действие вместо пользователя. Примеры из справки —
корректировка печати чека, добавление QR-кода. Создаются под ролью «Администратор системы».

Есть отдельный раздел «Использование триггеров в автономных приложениях» и упоминание,
что для работы с внешними сервисами Saby использует OAuth 2 — то есть теоретически
триггер может вызвать наш эндпоинт. Подтверждения, что это полноценный
webhook-механизм для выгрузки документов, найти не удалось.

**Вывод:** планируем polling через `СБИС.СписокИзменений`; триггеры как push-канал —
гипотеза для проверки на PoC.

## Часть VI. ⚠️ Главный технический вывод: позиций документа в JSON нет

В JSON-ответах ЭДО приходит **только шапка документа** — идентификатор, дата, номер,
общая сумма, тип, направление, состояние, контрагент, список вложений.
**Табличной части (товар, количество, цена, ставка и сумма НДС) в JSON нет.**

Позиции лежат внутри **формализованного XML-вложения формата ФНС** (УПД по приказу
ФНС от 19.12.2023 № ЕД-7-26/970). Справка делит вложения на формализованные
(регламентированный XML) и неформализованные (pdf, jpg и др.); API работает с обоими.

Рабочая схема для аналитики по SKU:

```
СписокИзменений (курсор) → СписокДокументов (шапки)
   → ПрочитатьДокумент (метаданные вложений)
      → GET по временной ссылке → УПД.xml
         → парсер ФНС-XML → позиции → маппинг на products / raw_materials
```

**Нужен парсер УПД в формате ФНС** — самостоятельный кусок работы, закладывать в оценку
сразу. Не исключено, что номенклатуру отдаёт `ДопПоля` метода `ПрочитатьДокумент`, но
по доступным источникам это не подтверждается. **Проверить первым делом на PoC** — от
ответа зависит объём этапа 3.

## Часть VII. Ограничения и режим работы

- **Вебхуков и колбэков для выгрузки нет** → только polling
- **Не более 5 параллельных потоков** запросов, иначе система вводит ограничения [офиц.]
- Аутентификация: ≤300 вызовов/мин с одного IP [втор.] → `sid`/`token` обязательно кешировать
- `Навигация.РазмерСтраницы` ≤ 200
- Вложение ≤ 73 МБ, до 10 вложений на документ [втор.]; с 18.03.2025 число вложений
  во внешнем ДО ограничено тарифом [офиц.]
- Временные ссылки на файлы живут ~1 месяц [втор.] — качать сразу, не хранить ссылку как данные
- **Разные форматы дат в контурах:** ЭДО — `ДД.ММ.ГГГГ`, Retail — `ГГГГ-ММ-ДД`
- Суммы приходят **строками** (`"150000.00"`) — приводить к `numeric` на входе
- Требования к ОС нет: подходит любая, поддерживающая HTTPS

| Данные | Откуда | Зачем |
|---|---|---|
| Исходящие реализации/УПД: клиент, дата, номенклатура, кол-во, цена, НДС | ЭДО + парсинг XML | **Факт продаж по SKU и клиентам** — сейчас в БД только себестоимость и прайсы |
| Входящие УПД от поставщиков сырья и упаковки | ЭДО + парсинг XML | **Фактические закупочные цены** → сверка с `material_prices`, план/факт себестоимости |
| Контрагенты (ИНН, КПП, название, идентификатор участника) | `СписокКонтрагентов` + ВОК | Справочник клиентов и поставщиков с обогащением |
| Статусы документооборота | `СписокДокументовПоСобытиям`, `СписокИзменений` | Контроль неподписанных/отклонённых отгрузок |
| Склады и складские документы | `sabyWarehouse.*` | Остатки сырья и готовой продукции |
| Номенклатура, прайс-листы, штрихкоды | Retail | Сверка нашего генератора прайсов с учётом |

**Витрины на выходе:**
- Маржа по SKU = цена реализации из СБИС − себестоимость из рецептур
- Продажи по SKU / клиенту / месяцу (шт, кг, выручка)
- План/факт по закупочным ценам сырья, дрейф себестоимости
- ABC по SKU и клиентам
- Покрытие производственного плана остатками

### Маппинг номенклатуры — самое трудоёмкое место

В документах позиция приходит текстом, по названию матчить нельзя. Опорные ключи:
`article` (уникален и в `products`, и в `raw_materials`) и штрихкод из Retail
(`withBarcode: true`). Нужна таблица сопоставления и экран разбора нераспознанных
позиций. У самого Saby для 1С есть отдельный инструмент сопоставления номенклатуры —
ровно по этой причине.

## Часть IX. Предлагаемая архитектура

```
Supabase Edge Function (Deno, cron)
  ├── auth: token/sid в кеше, повтор на 401
  ├── ingest: СписокИзменений(курсор) → СписокДокументов → ПрочитатьДокумент
  │            → скачивание XML-вложений → парсер ФНС-УПД
  └── upsert (идемпотентно по Идентификатор документа)
        ↓
schema sbis:
  sbis_raw_documents      -- сырой JSON + сырой XML, как пришло
  sbis_documents          -- шапки: id, тип, направление, дата, номер, сумма, состояние, контрагент
  sbis_document_items     -- позиции из XML: наименование, артикул, кол-во, цена, НДС
  sbis_counterparties     -- ИНН/КПП/название/идентификатор участника
  sbis_warehouses         -- склады (sabyWarehouse.List)
  sbis_stock              -- остатки
  sbis_nomenclature_map   -- сопоставление с products / raw_materials
  sbis_sync_log           -- курсор ИдентификаторСобытия, статусы прогонов
        ↓
views: продажи по SKU, маржа, план/факт закупок, ABC
```

Принципы: сырое сохраняем всегда (переразобрать можно, перезапросить — не всегда);
≤5 параллельных запросов; ночная догрузка истории отдельно от часового инкремента;
секреты — в Supabase secrets, в репозиторий не попадают.

## Часть X. Порядок подключения [польз.]

1. Зарегистрироваться на `online.sbis.ru`
2. Добавить организацию или ИП
3. Подключить нужный тариф (например, «Обмен с контрагентами» для ЭДО)
4. Добавить стороннее приложение в Saby:
   - указать ответственного сотрудника
   - выбрать доступные участки системы
   - указать внешние сайты для работы приложения
   - получить `app_client_id`, `app_secret`, `secret_key`
5. Настроить авторизацию (сервисную — для серверных интеграций)

### Чек-лист для старта

**Организационное (блокер):**
- [ ] Тариф: ЭДО API требует уровня «Обмен с контрагентами»; в минимальных тарифах
      средства интеграции с внешними системами недоступны. Уточнить у менеджера Тензора,
      что входит в текущий тариф и сколько стоит доступ к API
- [ ] Приложение-интеграция в ЛК → `app_client_id`, `app_secret`, `secret_key`
- [ ] Доступ к тестовому контуру `fix-online.sbis.ru`
- [ ] Список юрлиц (ИНН), складов, точек продаж

**Техническое:**
- [ ] Секреты в Supabase: `SBIS_APP_CLIENT_ID`, `SBIS_APP_SECRET`, `SBIS_SECRET_KEY`
      (+ `SBIS_LOGIN`/`SBIS_PASSWORD`, если понадобится сессионная авторизация)
- [ ] Схема `sbis` (см. Часть IX) + миграция
- [ ] Клиент к API, парсер ФНС-УПД, cron, журнал синхронизаций
- [ ] Разблокировать `api.sbis.ru` / `online.sbis.ru` в egress-политике среды разработки

## Часть XI. Открытые вопросы

1. **Где первоисточник учёта — СБИС или 1С?** Если учёт в 1С, а СБИС только канал ЭДО,
   дешевле тянуть из 1С (OData/HTTP-сервисы), и дизайн меняется целиком. **Главный вопрос.**
2. Отдаёт ли `ПрочитатьДокумент` номенклатуру через `ДопПоля`? Если да — парсер ФНС-XML
   не нужен, этап 3 схлопывается вдвое.
3. Покрывает ли сервисный токен (`X-SBISAccessToken`) методы JSON-RPC контура, или для
   них обязательна сессионная авторизация?
4. Есть ли Saby Retail / точки продаж — от этого зависит доступность REST-контура.
5. Можно ли использовать «Триггеры» как push-канал во внешнюю систему?
6. Какая витрина нужна первой: маржа по SKU или план/факт по закупкам сырья.

Вопросы 2 и 3 закрываются на этапе 1 (PoC) — они определяют объём остальных этапов.
