# Интеграция с СБИС / Saby (sbis.ru)

Исследование вариантов подключения к СБИС (с 2024 г. бренд — **Saby**, домены `sbis.ru`,
`saby.ru`, `online.sbis.ru`, API — `api.sbis.ru`) для обмена данными и построения
аналитических витрин на базе нашей БД.

> Статус документа: **аналитика перед стартом**. Часть деталей (точные имена полей,
> состав методов, доступность по тарифу) требует сверки по личному кабинету и
> документации — справка `saby.ru/help` отдаёт 403 на автоматические запросы,
> поэтому финальные схемы полей фиксируем на этапе PoC.

---

## 1. Из чего состоит API СБИС

СБИС — это не один API, а несколько независимых сервисов под общим хостом
`api.sbis.ru` с общей схемой авторизации. Доступность каждого зависит от того,
какие продукты подключены у компании.

| Сервис | Базовый адрес | Что даёт |
|---|---|---|
| **ЭДО** (электронный документооборот) | `online.sbis.ru/service/` (JSON-RPC 2.0, методы `СБИС.*`) | Входящие/исходящие документы: УПД, накладные, счета-фактуры, акты; их табличные части, контрагенты, статусы документооборота |
| **Розница / Бизнес (Retail)** | `api.sbis.ru/retail/...` (REST) | Номенклатура, прайс-листы, точки продаж, склады, остатки, продажи |
| **Онлайн-кассы и ОФД** | `api.sbis.ru/rent/v1/...` | Чеки, выручка, средний чек, список ККТ, кассовые смены |
| **«Всё о компаниях» (ВОК)** | `api.sbis.ru/vok/` | Реквизиты, финансы, надёжность, суды, лицензии по ИНН/ОГРН. [Открытая обвязка на GitHub](https://github.com/saby/vok) |
| Отчётность, КЭДО, CRM/salon | отдельные разделы | Нам не нужны |

Дополнительно существуют **SDK и локальный плагин СБИС** — они нужны для подписи
документов на рабочем месте пользователя, для аналитики не требуются.

## 2. Варианты подключения

### Вариант A — REST/JSON-RPC API напрямую (рекомендуемый)
Наш сервис ходит в `api.sbis.ru` по расписанию, складывает сырые ответы в staging-схему,
дальше строим витрины в PostgreSQL.

- **+** онлайн-режим, инкрементальные обновления, полный контроль над моделью данных
- **+** ложится на текущий стек (Supabase + Edge Functions), новых серверов не нужно
- **−** требует тарифа с разрешённой интеграцией и настройки приложения в ЛК

### Вариант B — файловый обмен (выгрузка XML/CSV из СБИС)
Ручная или полуручная выгрузка реестров документов, парсинг на нашей стороне.

- **+** ноль требований к тарифу и правам, можно начать завтра
- **−** не онлайн, ручной труд, ломается на любом изменении формата
- Годится как **запасной путь для исторической загрузки** за прошлые периоды.

### Вариант C — через 1С
Если учёт фактически ведётся в 1С, а СБИС используется только как канал ЭДО, —
данные дешевле тянуть из 1С (OData/HTTP-сервисы), а не из СБИС.

**Требует ответа: где «первоисточник» учёта — СБИС или 1С.** От этого зависит весь дизайн.

### Вариант D — плагин/SDK
Только подпись на клиенте. Для наших задач не применим.

## 3. Авторизация (вариант A)

Используется **сервисная авторизация** — для фоновых приложений без участия человека:

1. В личном кабинете `online.sbis.ru` создаётся приложение-интеграция →
   выдаются `app_client_id`, `app_secret` (client secret) и `secret_key`
   (ключ для приложений, работающих в фоне).
2. `POST https://online.sbis.ru/oauth/service/` с этими параметрами → в JSON-ответе
   поле `token`.
3. Токен передаётся в заголовке **каждого** запроса: `X-SBISAccessToken: <token>`.
   Без него команды API не обрабатываются.
4. В ЭДО-части (JSON-RPC) исторически используется сессия и заголовок
   `X-SBISSessionID` — сверяем на PoC, какой из механизмов актуален для нужных методов.

Токен живёт ограниченное время → в клиенте нужен автоматический перезапрос
при `401` и кеш токена (не дёргать авторизацию на каждый запрос).

## 4. Что реально можно вытащить и зачем это нам

Сопоставление с текущей схемой БД (`raw_materials`, `recipes`, `products`,
`price_lists`):

| Данные из СБИС | Метод/раздел | Что даёт проекту |
|---|---|---|
| **Исходящие реализации / УПД** (клиент, дата, номенклатура, кол-во, цена, сумма, НДС) | ЭДО: `СБИС.СписокДокументов`, `СБИС.ПрочитатьДокумент` | Факт продаж по SKU и клиентам — сейчас у нас есть только прайсы и себестоимость, факта нет |
| **Входящие УПД от поставщиков** сырья и упаковки | ЭДО, реестр «Входящие» | **Фактические закупочные цены** → сверка с `material_prices`, план/факт себестоимости, авто-обновление цен сырья |
| **Контрагенты** | `СБИС.ИнформацияОКонтрагенте` + ВОК по ИНН | Справочник клиентов и поставщиков с реквизитами, обогащение (надёжность, финансы) |
| **Статусы документооборота** (подписан / отклонён / ждёт) | `СБИС.СписокДокументовПоСобытиям`, `СБИС.СписокИзменений` | Контроль незакрытых отгрузок; `СписокИзменений` — основа инкрементальной синхронизации |
| **Номенклатура и прайс-листы** | `api.sbis.ru/retail/nomenclature/list`, `.../nomenclature/price-list` | Сверка нашего прайс-генератора с тем, что реально заведено в учёте |
| **Остатки по складам** | `retail/company/list` → `retail/company/warehouses?companyId=…` → остатки | Остатки сырья и готовой продукции рядом с рецептурами — расчёт «на сколько хватит сырья по плану производства» |
| **Точки продаж, продажи, чеки** | `retail/point/list`, продажи; ОФД: `api.sbis.ru/rent/v1/groups/<groupId>/report/?salespoint=…&dateFrom=…&dateTo=…` | Актуально только если есть розница/касса |

**Чего в СБИС нет и не будет:** рецептур, нормативной себестоимости, состава SKU —
это остаётся нашей зоной. Ценность интеграции именно в стыке: *наша себестоимость ×
их факт продаж и закупок*.

### Витрины, которые получаем на выходе
- Продажи по SKU / клиенту / месяцу (шт, кг, выручка)
- **Маржа по SKU** = цена реализации из СБИС − себестоимость из рецептур
- План/факт по закупочным ценам сырья, дрейф себестоимости во времени
- ABC/XYZ по SKU и клиентам, динамика отгрузок
- Покрытие остатками производственного плана

## 5. Что нужно, чтобы начать

**Со стороны СБИС (организационное):**
1. Действующий аккаунт `online.sbis.ru` и **тариф, в котором разрешена интеграция** —
   в минимальных тарифах ЭДО средства интеграции с внешними системами недоступны,
   лицензия на API докупается отдельно. Уточнить у менеджера Тензора: что именно
   входит в текущий тариф и сколько стоит доступ к API.
2. Список организаций (ИНН) и складов, по которым нужны данные.
3. Пользователь/сотрудник с правами на нужные разделы, от имени которого работает
   приложение.
4. Созданное приложение-интеграция → `app_client_id`, `app_secret`, `secret_key`.

**С нашей стороны (техническое):**
1. Секреты в Supabase (`SBIS_APP_CLIENT_ID`, `SBIS_APP_SECRET`, `SBIS_SECRET_KEY`) —
   в репозиторий не попадают.
2. Схема `sbis` в БД: staging-таблицы с сырым JSON + нормализованные
   `sbis_counterparties`, `sbis_documents`, `sbis_document_items`, `sbis_stock`.
3. **Таблица сопоставления номенклатуры** `sbis_nomenclature_map`
   (`sbis_nomenclature_id`/`код`/`штрихкод` → `products.id` / `raw_materials.id`).
   Это критичный и самый трудоёмкий пункт: в документах номенклатура приходит
   строкой, по названию сматчить надёжно нельзя. Опора — `article`
   (в `products` и `raw_materials` он уникален) и штрихкод.
4. Edge Function на Deno (auth + пагинация + ретраи с backoff) + расписание
   (pg_cron / scheduled function), идемпотентный upsert по идентификатору документа.
5. Журнал синхронизаций (`sbis_sync_log`) с курсором по дате/`СписокИзменений`.

## 6. Риски и открытые вопросы

- **Тариф.** Доступность методов зависит от подключённых продуктов. До проверки
  доступа любые сроки — оценочные.
- **Лимиты запросов** публично не описаны → закладываем backoff и ночную загрузку истории.
- **Сопоставление номенклатуры** — главный источник грязи в данных. Нужен ручной
  разбор нераспознанных позиций (интерфейс «неразобранное» в админке).
- **Первоисточник учёта** — СБИС или 1С (см. вариант C).
- Документация saby.ru закрыта для автоматического чтения (403), точные форматы
  полей фиксируем по реальным ответам на PoC.

## 7. План работ

| Этап | Содержание | Результат |
|---|---|---|
| 0 | Проверка тарифа, создание приложения, получение ключей | Есть доступ |
| 1 | PoC: сервисная авторизация + один метод (список исходящих документов за месяц) | Подтверждён формат ответа |
| 2 | Схема `sbis` + загрузчик документов с инкрементом | Сырые данные в БД |
| 3 | Маппинг номенклатуры + интерфейс разбора нераспознанного | Документы связаны с SKU |
| 4 | Аналитические view + страницы в приложении | Маржа, продажи, план/факт закупок |

Этапы 1–2 упираются только в этап 0; без ответа по тарифу стартовать нельзя.
