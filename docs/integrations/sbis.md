# Интеграция с СБИС / Saby (sbis.ru)

Техническое исследование подключения к СБИС (с 2024 г. бренд — **Saby**; домены
`sbis.ru`, `saby.ru`, личный кабинет `online.sbis.ru`, API `api.sbis.ru`) для
обмена данными и построения аналитических витрин поверх нашей БД.

> **Как собиралась информация.** Справка `saby.ru/help` и хосты `sbis.ru`,
> `api.sbis.ru`, `online.sbis.ru` недоступны из среды разработки — egress-политика
> отдаёт 403 на CONNECT, живые запросы к API отсюда невозможны в принципе.
> Данные собраны из выдачи официальной справки в поиске и из разбора исходников
> публичных клиентских библиотек (npm `sbis-mcp`, PyPI `sbis-api-client`), где
> эндпоинты, параметры и форматы зафиксированы в коде. Первичные источники
> помечены в разделе «Источники»; всё, что взято из библиотек, помечено
> **[втор.]** и подлежит проверке на PoC.

---

## 1. Два независимых контура API

Это ключевой факт: у СБИС не один API, а **два разных контура с разной
авторизацией и разным стилем**. Их нельзя смешивать.

| | Контур ЭДО | Контур Retail / Бизнес |
|---|---|---|
| Стиль | JSON-RPC 2.0, методы `СБИС.*` кириллицей | REST, GET с query-параметрами |
| Точка входа | `POST https://online.sbis.ru/service/?srv=1` | `https://api.sbis.ru/retail/...` |
| Авторизация | `СБИС.Аутентифицировать` (логин/пароль) → `sid` | OAuth-подобная сервисная (3 ключа) → `token` |
| Заголовок | `X-SBISSessionID: <sid>` | `X-SBISAccessToken: <token>` |
| Content-Type | `application/json-rpc; charset=utf-8` | обычный REST |
| Что даёт | документы ЭДО, контрагенты, статусы ДО | номенклатура, прайсы, остатки, точки продаж, заказы |
| Требует | тариф уровня «Обмен с контрагентами» | подключённый Saby Retail / точки продаж |

Плюс два периферийных контура: **ОФД/аренда** (`api.sbis.ru/rent/v1/...` — выручка,
чеки, ККТ, смены) и **«Всё о компаниях»** (`api.sbis.ru/vok/` — реквизиты, финансы,
надёжность по ИНН/ОГРН, [открытая обвязка на GitHub](https://github.com/saby/vok)).

**Тестовый контур:** `https://fix-online.sbis.ru` вместо `online.sbis.ru` — PoC гоняем там.

## 2. Авторизация

### 2.1. ЭДО: сессионная

```jsonc
POST https://online.sbis.ru/auth/service/
Content-Type: application/json-rpc; charset=utf-8

{ "jsonrpc": "2.0", "method": "СБИС.Аутентифицировать",
  "params": { "Параметр": { "Логин": "...", "Пароль": "...",
                            "НомерАккаунта": "..." } },   // НомерАккаунта — если аккаунтов несколько
  "id": 0 }
```

В ответе `result` — строка с идентификатором сессии (`sid`). Дальше каждый вызов:

```jsonc
POST https://online.sbis.ru/service/?srv=1
X-SBISSessionID: <sid>

{ "jsonrpc": "2.0", "method": "СБИС.СписокДокументов", "params": {...}, "id": 1 }
```

Ответ — стандартный JSON-RPC: `result` при успехе, `error.message`/`error.code` при
ошибке. На `HTTP 401` нужно переаутентифицироваться и повторить вызов; на `5xx` —
один ретрай. **[втор.]**

**Время жизни сессии:** источники расходятся — официальная справка (раздел «Порядок
работы») говорит про аннулирование через 24 часа простоя и максимум 7 дней с момента
получения, сторонняя библиотека — про ~21 день. Практический вывод один: `sid` кешируем
в памяти, ловим 401, переавторизуемся. Точное значение неважно.

### 2.2. Retail: сервисная (токен)

```jsonc
POST https://online.sbis.ru/oauth/service/
{ "app_client_id": "...", "app_secret": "...", "secret_key": "..." }
→ { "token": "...", "sid": "..." }
```

Три ключа выдаются при создании приложения-интеграции в личном кабинете.
Дальше — `X-SBISAccessToken: <token>` в каждом запросе. Выход:
`POST /oauth/service/ {"event": "exit", "token": "..."}`. **[втор.]**

## 3. Методы контура ЭДО

### `СБИС.СписокДокументов` — реестр документов по типу и периоду

```jsonc
{ "Фильтр": {
    "Тип": "Реализация",              // обязательный: Реализация, Корреспонденция, ДокОтгрИсх, …
    "ДатаС": "01.06.2026",            // формат ДД.ММ.ГГГГ, не ISO
    "ДатаПо": "30.06.2026",
    "Направление": "Исходящий",       // Входящий | Исходящий
    "Состояние": "...",
    "Маска": "...",                   // поиск по Документ.Номер и Документ.Примечание
    "Контрагент": { "СвЮЛ": { "ИНН": "7700000000", "КПП": "770001001" } },
    "Навигация": { "Страница": "0", "РазмерСтраницы": "200" }   // РазмерСтраницы ≤ 200
} }
```

Ответ:

```jsonc
{ "Документ": [ {
      "Идентификатор": "…", "Дата": "15.06.2026", "Номер": "АКТ-001",
      "Сумма": "150000.00", "Название": "…", "Тип": "Реализация",
      "Направление": "Входящий", "ДатаВремяСоздания": "15.06.2026 10.30.00",
      "Удален": "Нет",
      "Состояние": { "Код": "7", "Название": "Доставлен", "Примечание": "" },
      "Контрагент": { "СвЮЛ": { "ИНН": "…", "КПП": "…", "Название": "…" } },
      "Вложение": [ { "Идентификатор": "…", "Название": "Акт.pdf", "Тип": "АктВыпРаб" } ]
  } ],
  "Навигация": { "РазмерСтраницы": "50", "Страница": "0", "ЕстьЕще": "Нет" } }
```

Пагинация — по `Навигация.ЕстьЕще` («Нет»/«Да»), листаем `Страница`.

### `СБИС.СписокДокументовПоСобытиям` — реестры «Входящие» / «Исходящие» / «Ответы от контрагентов»

Фильтр тот же, но вместо `Тип` — `ТипРеестра`. Ответ обёрнут в `Реестр: [{ Состояние, Документ }]`.

### `СБИС.СписокИзменений` — **основа инкрементальной синхронизации**

Возвращает документы, по которым были события документооборота за период.
Работает как курсор: первый запрос — по `ДатаВремяС`, дальше передаём
`ИдентификаторСобытия` последнего события предыдущей страницы. Именно это
храним в журнале синхронизаций, а не «дату последней загрузки».

### `СБИС.ПрочитатьДокумент` — карточка документа

```jsonc
{ "Документ": { "Идентификатор": "…", "Редакция": { "Идентификатор": "…" } },
  "ДопПоля": "…" }
```

Возвращает последнюю (или указанную) редакцию + метаданные вложений с
**временными ссылками на файлы**:

```jsonc
"Вложение": [ { "Идентификатор": "…", "Название": "УПД.xml", "Тип": "УПД",
                "Файл": { "Имя": "UPD_example.xml", "Ссылка": "https://online.sbis.ru/docs/…" } } ]
```

Ссылка самодостаточна — качается обычным GET без `sid`, живёт ~1 месяц. **[втор.]**

### Прочее

- `СБИС.СписокКонтрагентов` — `{"Фильтр": {"ИНН", "КПП", "Название", "Навигация"}}` →
  `Контрагент[]` с `Идентификатор`, `СвЮЛ`/`СвФЛ`, `ИдентификаторУчастника`
  (вида `2BM-ИНН-КПП-…`).
- `СБИС.СписокНашихОрганизаций` — свои юрлица. **[втор.]**
- `СБИС.ИнформацияОТекущемПользователе`, `СБИС.ИнформацияОКонтрагенте`.
- Запись (нам на первом этапе не нужна): `СБИС.ЗаписатьДокумент`,
  `СБИС.ЗаписатьВложение`, `СБИС.ПодготовитьДействие`, `СБИС.ВыполнитьДействие`.
- Визуализация: представление документа в HTML/PDF по GET-ссылке из объекта «Документ».

## 4. ⚠️ Главный технический вывод: позиций документа в JSON нет

В JSON-ответах ЭДО приходит **только шапка документа** — идентификатор, дата, номер,
общая сумма, тип, направление, состояние, контрагент, список вложений.
**Табличной части (товар, количество, цена, ставка и сумма НДС) в JSON нет.**

Позиции лежат внутри **формализованного XML-вложения формата ФНС** (УПД по приказу
ФНС от 19.12.2023 № ЕД-7-26/970). Справка прямо делит вложения на формализованные
(регламентированный XML) и неформализованные (pdf, jpg и пр.).

Отсюда рабочая схема для аналитики по SKU:

```
СписокИзменений (курсор) → СписокДокументов (шапки)
   → ПрочитатьДокумент (метаданные вложений)
      → GET по временной ссылке → УПД.xml
         → парсер ФНС-XML → позиции → маппинг на products / raw_materials
```

То есть **нужен парсер УПД в формате ФНС** — это самостоятельный кусок работы,
и его надо закладывать в оценку сразу. Возможность получить номенклатуру напрямую
через `ДопПоля` метода `ПрочитатьДокумент` не исключена, но по доступным источникам
не подтверждается — проверяем первым делом на PoC, потому что от ответа зависит
объём этапа 3.

## 5. Методы контура Retail

Подтверждены исходниками `sbis-api-client` **[втор.]**:

| Эндпоинт | Параметры | Отдаёт |
|---|---|---|
| `GET /retail/point/list` | `pointId`, `product`, `withPhones`, `withPrices`, `withSchedule`, `page`, `pageSize` | точки продаж |
| `GET /retail/nomenclature/price-list` | `pointId`, `actualDate` (ГГГГ-ММ-ДД), `searchString`, `page`, `pageSize` | действующие прайс-листы |
| `GET /retail/nomenclature/list` | `pointId`, `priceListId`, `withBalance`, `withBarcode`, `onlyPublished`, `page`, `pageSize` | товары и услуги по прайсу |
| `GET /retail/nomenclature/balances` | `nomenclatures[]`, `priceListIds[]`, `warehouses[]`, `companies[]` | остатки на складах |
| `GET /retail/company/list`, `/retail/company/warehouses?companyId=` | — | организации и их склады |
| `GET /retail/customer/find?phone=`, `/retail/customer/{id}/bonus-balance` | — | клиенты, бонусы |
| `/retail/order/{externalId}`, `/update`, `/cancel`, `/state`, `/payment-link`, `/register-payment` | — | заказы и оплаты |

Важные оговорки:
- Прайс-лист отдаётся корректно только если он настроен с типом **«Выбранные наименования»**.
- `withBarcode: true` в `nomenclature/list` — наш способ вытащить штрихкоды, а они
  нужны для маппинга (см. §7).
- Встречается упоминание версии `/retail/v2/nomenclature/list` — уточнить актуальную.
- **Весь этот контур завязан на Saby Retail / точки продаж.** Для оптового
  производства без розницы он может быть просто недоступен, и тогда остатки и
  номенклатуру брать неоткуда, кроме складского учёта. Это вопрос №1 к менеджеру Тензора.

## 6. Ограничения и режим работы

- **Вебхуков и колбэков нет.** Только polling. Отсюда — `СписокИзменений` с курсором
  и расписание.
- **Не более 5 параллельных потоков** запросов, иначе система вводит ограничения.
- Аутентификация: ≤300 вызовов/мин с одного IP **[втор.]** → `sid`/`token` обязательно кешировать.
- `Навигация.РазмерСтраницы` ≤ 200.
- Вложение ≤ 73 МБ, до 10 вложений на документ **[втор.]**; с 18.03.2025 число
  вложений во внешнем ДО ограничено тарифом.
- Временные ссылки на файлы живут ~1 месяц **[втор.]** — качаем сразу, не храним ссылку как данные.
- Даты: в ЭДО — `ДД.ММ.ГГГГ`, в Retail — `ГГГГ-ММ-ДД`. Разные форматы в разных контурах.
- Суммы приходят **строками** (`"150000.00"`) — приводить к `numeric` на входе.

## 7. Что это даёт проекту

Сопоставление с текущей схемой (`raw_materials`, `recipes`, `products`, `price_lists`):

| Данные | Откуда | Зачем нам |
|---|---|---|
| Исходящие реализации/УПД: клиент, дата, номенклатура, кол-во, цена, НДС | ЭДО + парсинг XML | **Факт продаж по SKU и клиентам** — сейчас в БД есть себестоимость и прайсы, факта нет вообще |
| Входящие УПД от поставщиков сырья и упаковки | ЭДО + парсинг XML | **Фактические закупочные цены** → сверка с `material_prices`, план/факт себестоимости, автоподстановка цен |
| Контрагенты (ИНН, КПП, название, идентификатор участника) | `СписокКонтрагентов` + ВОК | Справочник клиентов и поставщиков с обогащением |
| Статусы документооборота | `СписокДокументовПоСобытиям`, `СписокИзменений` | Контроль неподписанных/отклонённых отгрузок |
| Номенклатура, прайс-листы, штрихкоды | Retail | Сверка нашего генератора прайсов с учётом |
| Остатки по складам | Retail `nomenclature/balances` | Покрытие производственного плана сырьём |

Витрины на выходе: маржа по SKU (цена реализации из СБИС − себестоимость из
рецептур), продажи по SKU/клиенту/месяцу, дрейф закупочных цен, ABC по SKU и клиентам,
остатки против плана.

**Чего в СБИС нет:** рецептур, нормативной себестоимости, состава SKU. Ценность
интеграции ровно в стыке: *наша себестоимость × их факт*.

### Маппинг номенклатуры — самое трудоёмкое место

В документах позиция приходит текстом, по названию матчить нельзя. Опорные ключи:
`article` (уникален и в `products`, и в `raw_materials`) и штрихкод из Retail
(`withBarcode: true`). Нужна таблица `sbis_nomenclature_map` и экран разбора
нераспознанных позиций — без ручного контура здесь не обойтись, у самого СБИС для
1С есть отдельный инструмент сопоставления номенклатуры ровно по этой причине.

## 8. Архитектура на нашем стеке

```
Supabase Edge Function (Deno, cron)
  ├── auth: sid (ЭДО) и token (Retail) в кеше, повтор на 401
  ├── ingest: СписокИзменений(курсор) → СписокДокументов → ПрочитатьДокумент
  │            → скачивание XML-вложений → парсер ФНС-УПД
  └── upsert (идемпотентно по Идентификатор документа)
        ↓
schema sbis:
  sbis_raw_documents      -- сырой JSON + сырой XML, как пришло
  sbis_documents          -- шапки: id, тип, направление, дата, номер, сумма, состояние, контрагент
  sbis_document_items     -- позиции из XML: наименование, артикул, кол-во, цена, НДС
  sbis_counterparties     -- ИНН/КПП/название/идентификатор участника
  sbis_stock              -- остатки (если Retail доступен)
  sbis_nomenclature_map   -- сопоставление с products / raw_materials
  sbis_sync_log           -- курсор ИдентификаторСобытия, статусы прогонов
        ↓
views: продажи по SKU, маржа, план/факт закупок, ABC
```

Принципы: сырое сохраняем всегда (переразобрать можно, перезапросить — не всегда);
не более 5 параллельных запросов; ночная догрузка истории отдельно от часового
инкремента; секреты — в Supabase secrets, в репозиторий не попадают.

## 9. Что нужно, чтобы начать

**Организационное (блокер):**
1. **Тариф.** ЭДО API требует тариф уровня «Обмен с контрагентами» — в минимальных
   тарифах средства интеграции с внешними системами недоступны. Retail API требует
   подключённого Saby Retail. Вопрос менеджеру Тензора: что входит в наш текущий
   тариф, что докупать, сколько стоит.
2. Приложение-интеграция в ЛК → `app_client_id`, `app_secret`, `secret_key`
   (для Retail) и служебная учётка логин/пароль (для ЭДО).
3. Доступ к тестовому контуру `fix-online.sbis.ru`.
4. Список наших юрлиц (ИНН), складов, точек продаж.

**Техническое:**
1. Секреты в Supabase: `SBIS_LOGIN`, `SBIS_PASSWORD`, `SBIS_APP_CLIENT_ID`,
   `SBIS_APP_SECRET`, `SBIS_SECRET_KEY`.
2. Схема `sbis` (§8) + миграция.
3. Клиент к обоим контурам, парсер ФНС-УПД, cron, журнал синхронизаций.
4. **Разблокировать `api.sbis.ru` / `online.sbis.ru` в egress-политике среды
   разработки** — сейчас они закрыты, из этой среды PoC не запустить.

## 10. Открытые вопросы

1. **Где первоисточник учёта — СБИС или 1С?** Если учёт в 1С, а СБИС только канал
   ЭДО, дешевле тянуть из 1С (OData/HTTP-сервисы), и дизайн меняется целиком.
2. Есть ли Saby Retail / точки продаж — от этого зависит доступность остатков и номенклатуры.
3. Отдаёт ли `ПрочитатьДокумент` номенклатуру через `ДопПоля` — если да, парсер ФНС-XML
   не нужен и этап 3 схлопывается вдвое.
4. Какая витрина нужна первой: маржа по SKU или план/факт по закупкам сырья.

## 11. План работ

| Этап | Содержание | Блокируется |
|---|---|---|
| 0 | Тариф, приложение в ЛК, ключи, доступ к `fix-online`, разблокировка хостов | — |
| 1 | PoC: обе авторизации + `СписокНашихОрганизаций` + `СписокДокументов` за месяц + чтение одного УПД целиком | этап 0 |
| 2 | Схема `sbis`, загрузчик шапок с инкрементом по `СписокИзменений` | этап 1 |
| 3 | Скачивание и парсинг XML-вложений → позиции | этап 2 + ответ на вопрос №3 |
| 4 | Маппинг номенклатуры + экран разбора нераспознанного | этап 3 |
| 5 | Витрины и страницы в приложении | этап 4 |

Ответ на вопрос №3 (§10) стоит получить на этапе 1 — он определяет объём этапа 3.
